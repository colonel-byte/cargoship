Cargoship

Cargoship is a Go-based CLI for building, distributing, and applying offline Kubernetes distro packages. It is designed to simplify two core workflows:

  1. Package Creation: Building a self-contained, offline Kubernetes distro package containing everything needed for installation in disconnected or highly-regulated environments.
  2. Cluster Lifecycle Management: Bootstrapping, upgrading, and managing the cluster on target hosts over SSH using the packaged distribution.

Cargoship bridges the gap between offline distro packaging tools and remote cluster lifecycle managers, supporting OCI image and file packaging, secure publishing to OCI registries, and robust SSH orchestration.

Installation

Pre-built binaries

Every release publishes archives for Linux, macOS, and Windows across amd64, arm64, and riscv64. The name carries the OS and the architecture, with amd64 spelled the way uname -m does, so the one for a 64-bit Linux host is cargoship_Linux_x86_64.tar.gz and the arm64 one is cargoship_Linux_arm64.tar.gz:

VERSION=$(curl -fsSL https://api.github.com/repos/colonel-byte/cargoship/releases/latest | grep -o '"tag_name": *"[^"]*"' | cut -d'"' -f4)
curl -fsSLO "https://github.com/colonel-byte/cargoship/releases/download/${VERSION}/cargoship_Linux_x86_64.tar.gz"
tar -xzf cargoship_Linux_x86_64.tar.gz cargoship
install -m 0755 cargoship /usr/local/bin/cargoship

Linux packages

Releases also carry .rpm, .deb, and .apk packages. Each installs the binary, shell completions for bash, fish and zsh, and the colonel_byte.cargoship Ansible collection onto ansible-core’s default collection path:

sudo dnf install ./cargoship_*_linux_amd64.rpm    # or: sudo apt install ./cargoship_*_linux_amd64.deb

Container images

podman run --rm ghcr.io/colonel-byte/cargoship:latest version
ImageContents
ghcr.io/colonel-byte/cargoshipThe binary on a minimal base
ghcr.io/colonel-byte/cargoship-ubiThe binary installed from the .rpm, on AlmaLinux 10
ghcr.io/colonel-byte/cargoship-debThe binary installed from the .deb, on Debian slim

The -ubi name is historical: that image was based on Red Hat UBI and is now built on AlmaLinux 10, but the published image name has not changed.

From source

Building needs Go 1.27 or newer.

go install github.com/colonel-byte/cargoship@latest

That reaches the network for the module. To build without it, clone the repository instead: the vendor/ tree is committed, so a clone builds with no network access at all, which is how a management node inside an airlock is staged.

git clone https://github.com/colonel-byte/cargoship.git && cd cargoship
mage build:binary    # or: go run ./magefiles/core build:binary

Verifying a download

Release archives and container images are signed with Cosign, using the key published at cosign.pub. Each archive ships a .sigstore.json bundle beside it, and every release carries a checksums.txt:

cosign verify-blob --key cosign.pub --bundle cargoship_Linux_x86_64.tar.gz.sigstore.json cargoship_Linux_x86_64.tar.gz
cosign verify --key cosign.pub ghcr.io/colonel-byte/cargoship:latest

Core Concepts

Cargoship is built around two primary architectural concepts:

1. Offline Distro Packages

A Cargoship package is a single, compressed archive containing all artifacts necessary to spin up or upgrade a Kubernetes cluster in air-gapped networks. It bundles:

  • Distro-specific metadata and layout descriptors.
  • Required engine configuration templates and system files.
  • OCI images and container artifacts.
  • Checksums and cryptographic signatures for integrity verification.

The package compilation process loads a local distro definition, gathers all specified assets, and produces a single, verifiable archive.

2. Phase-Based Orchestration

Cluster operations are modeled as ordered sequences of reusable, structured “phases.” This makes high-level actions (apply, prepare, reset, kube-config, engine-config-sync) predictable, easier to debug, and simple to extend.

For example, the apply workflow runs these phases, in this order:

  1. Connect: Establish secure SSH connections to all target hosts.
  2. OS Detection & Fact Gathering: Identify host operating systems, network facts, and the engine version already installed.
  3. Validation: Verify that host nodes meet the prerequisites, and stop if the cluster holds a node the config does not.
  4. Lock: Take an exclusive host lock, held for the rest of the run, so a second cargoship cannot change the same hosts.
  5. Prepare: Install OS packages, configure sysctl and environment, SELinux and fapolicyd rules, /etc/hosts, and the node firewall.
  6. Upload: Securely transfer package binaries, RPMs or DEBs, configuration templates, and OCI images to the nodes, then import the images. Image tarballs the package no longer carries are removed from the nodes in the same pass – see Image Tarballs on a Node.
  7. Bootstrap / Upgrade: Render the engine config, initialize control-plane nodes, apply bundled manifests, join workers, and upgrade any node already running an older version.
  8. Engine Config Sync: Reconcile registry, audit, and pod-security config on any node whose config drifted.
  9. Kubeconfig Retrieval and Labelling: Fetch the generated admin credentials and label nodes with their profile group.
  10. Cleanup & Disconnect: Release the lock, clean up temporary artifacts, and close SSH sessions.

The generated reference in docs/phases/ is the authoritative list, including what each phase does under --dry-run.

Usage Examples

Here are the standard workflows for compiling and deploying offline Kubernetes packages with Cargoship.

The commands that change a host - prepare, apply, reset, and engine-config-sync - will not do so without --confirm. Swap it for --dry-run to connect to every host and run the preflight checks for real, reporting what the run would change without changing it.

1. Compile an Offline Package

To build an offline archive containing all required files, binaries, and container images:

# Create a package from the current directory structure
cargoship create .

# Build from a specific path and output to a custom directory
cargoship create ./distro-defs -o ./build/

A build normally fetches the images and files a definition declares from the registries and URLs it names. Where that content has already been collected with hauler or zarf and carried across the airlock, point the build at that store instead and nothing is fetched:

# A hauler store directory, or an archive written by `hauler store save`
cargoship create ./distro-defs --content-store ./haul.tar.zst

# A built zarf package
cargoship create ./distro-defs --content-store ./zarf-package-rke2-content-amd64.tar.zst

Which format the store is comes from what it holds, not from what it is called. Images and files are matched against the reference each tool recorded for the artifact when it was collected, so no mapping has to be written by hand. Anything the store does not hold still comes from its declared source, which makes a partial store usable. A zarf package covers one architecture, so pass --architecture when building a multi-architecture definition from one. The same setting lives in the config file:

distro:
  create:
    content_store: ~/hauls/haul.tar.zst

See Building From a Local Content Store for the collect-and-carry workflow, what each format must contain, and how this compares with --registry-override and --file-override.

Where the build host can reach a registry, a file can also name an OCI reference directly, which is how a growing number of vendors publish air-gapped engine bundles. The entry says which layer it wants and selector.arch supplies the platform, so one tag covering several architectures resolves per entry:

spec:
  config:
    os:
      files:
        # one tarball per platform, published as a single titled layer
        - source: oci://registry.example.com/vendor/engine:v1.37.1
          extractPath: bin/engine
          target: /usr/local/bin/engine
          executable: true
          selector:
            arch:
              - amd64

        # every file in the release as its own titled layer
        - source: oci://ghcr.io/cri-o/bundle:d816c7e
          layer: cri-o/bin/crio
          target: /usr/local/bin/crio
          executable: true
          selector:
            arch:
              - amd64

--registry-override redirects these the way it redirects an image pull. See Declaring a File From an OCI Registry.

A build caches what it fetches under ~/.cache/cargoship, so a rebuild of the same definition reaches the network for little or nothing. Nothing expires that cache – it has no size limit and grows for as long as definitions name new versions – so clean-cache is what reclaims it:

# report every area with its size and what would go, removing nothing
cargoship dev clean-cache --dry-run

# keep anything fetched in the last fortnight, drop the rest
cargoship dev clean-cache --older-than 336h

# remove every fetchable area
cargoship dev clean-cache

Run logs and the local dev fleet’s images are never removed, and neither is an area this version does not recognise. An age window cannot prune the image layout, which is an index over shared blobs; it is reported as skipped and comes out whole when --older-than is omitted.

2. Prepare Target Nodes

Verify and configure OS-level prerequisites (such as kernel modules, firewall ports, fapolicyd rules, and /etc/hosts) across target machines using your cluster configuration inventory:

cargoship prepare ./build/cargoship-distro-amd64.tar.zst --config ./cargoship-config.yaml --confirm

3. Deploy or Upgrade a Cluster

Bootstrap a new cluster or upgrade an existing one from the compiled package:

cargoship apply ./build/cargoship-distro-amd64.tar.zst --config ./cargoship-config.yaml --confirm

An apply reconciles the node’s image directory as well as filling it: a tarball the package has stopped carrying – including the older tag of an image a version bump replaced – is deleted from every node, and so is a tarball sitting there that no cargoship run recorded. On a node where something other than cargoship also stages images, keep those by creating a marker file in the image directory, which leaves the package’s own images reconciled as normal:

# on the node: keep image tarballs cargoship did not upload, and warn about them every run
sudo touch /var/lib/rancher/k3s/agent/images/cargoship-keep-images

Image Tarballs on a Node covers the naming, both cleanups, and how a kept file is reported.

4. Fetch the Kubeconfig

Retrieve the admin kubeconfig securely from the primary controller:

cargoship kube-config --config ./cargoship-config.yaml

5. Uninstall or Reset Target Nodes

Stop, uninstall, and completely purge the Kubernetes distro and its state from the target hosts:

cargoship reset --config ./cargoship-config.yaml --distro rke2 --confirm

6. Generate an Inventory from Ansible

Translate an Ansible inventory you already maintain into a cargoship cluster inventory, taking each host’s role from its Ansible groups:

cargoship inventory from-ansible ./resolved.json -o ./inventory.yaml

7. Publish, Pull, Sign, and Verify a Package

A package can live in an OCI registry rather than on a disk, and every command that takes a package takes an oci:// reference wherever it takes a path:

# Push a built package to a registry
cargoship publish ./build/cargoship-distro-amd64.tar.zst oci://ghcr.io/my-org

# Pull one back down to a local directory
cargoship pull oci://ghcr.io/my-org/my-package:1.0.0 -o ./build/

# Sign a package with a private key
cargoship sign ./build/cargoship-distro-amd64.tar.zst --signing-key ./private-key.pem

# Verify the signature before anything installs from it
cargoship verify ./build/cargoship-distro-amd64.tar.zst --key ./cosign.pub

An operator who cannot reach the registry from the management node moves the package across the airlock with Skopeo instead, then converts the resulting OCI archive into a native package:

# On the connected side: export the package as an OCI archive
skopeo copy --override-os multi docker://ghcr.io/my-org/my-package:1.0.0 oci-archive:my-package.tar:1.0.0

# On the disconnected side: convert it into a package apply can install
cargoship import ./my-package.tar -o ./build/

import reads an OCI Image Layout, as a .tar or as an unpacked directory; see Importing Archives for the other tools that write one, and why a docker-archive cannot carry a package.

A cosign keypair is the only signing method - keyless (Fulcio/OIDC) signing and verification were removed, because they need network the management node does not have; see #848. The commands that load a package - apply, prepare, engine-config-sync, publish, pull, import, validate, schema - verify as part of loading, gated on --verify=never|if-possible|always. verify does nothing but check the signature, which is what makes it the one to run before a playbook.

8. Mirror a Package’s Contents into a Registry

publish uploads a package as one artifact, to be pulled back as a package. mirror does the opposite: it unpacks what the package carries into a registry as individually pullable content, so the mirror a fleet already pulls through holds what its nodes will ask for.

# Push every image and file the package carries into a registry
cargoship mirror ./build/cargoship-distro-amd64.tar.zst oci://harbor.internal

# Under a repository prefix, which most hosted registries require
cargoship mirror ./build/cargoship-distro-amd64.tar.zst oci://harbor.internal/cargoship

# Or read the destination from the registry proxy the cluster config already declares
cargoship mirror ./build/cargoship-distro-amd64.tar.zst --config ./cluster.yaml

# Only the images, against a registry on plain HTTP
cargoship mirror ./build/cargoship-distro-amd64.tar.zst oci://registry.internal:5000 --images --plain-http

An image keeps its repository path and its tag, and only the registry host changes: registry.k8s.io/pause:3.10 is pushed as harbor.internal/pause:3.10. That is not cosmetic - it is exactly what a node asks a mirror for, because apply writes that same proxy address into each host’s containerd configuration from spec.config.registries[].proxy.url. Passing --config reads the destination from that one field, so what gets pushed and what the nodes ask for cannot drift apart.

See Mirroring to a Registry for the naming rules, and how this compares with --registry-override and --content-store.

9. Encrypt Credentials in a Config File

Registry credentials in a cluster inventory are encrypted at rest, with Ansible Vault or with age. The vault command group covers both:

# Encrypt one value for a registry's user/pass/token field
cargoship vault encrypt my-registry-password --vault-password-file ./vault-pass.txt

# Encrypt or decrypt every registry credential in a config file, in place
cargoship vault encrypt-file ./cargoship-config.yaml --vault-password-file ./vault-pass.txt
cargoship vault decrypt-file ./cargoship-config.yaml --vault-password-file ./vault-pass.txt

# Encrypt the values already sitting at given YAML paths, naming each one
cargoship vault encrypt-path ./cargoship-config.yaml '.spec.config.registries[0].auth.pass' --vault-password-file ./vault-pass.txt

# Generate an age key pair, and re-wrap an existing file under a new key
cargoship vault keygen
cargoship vault rekey ./cargoship-config.yaml --new-vault-password-file ./new-pass.txt

encrypt-path only encrypts; cargoship decrypts a registry’s auth.user, auth.pass, auth.token and tls.ca at apply time, and warns when asked to encrypt a path outside that set. decrypt, decrypt-path, decrypt-file and encrypt-file complete the set; cargoship vault --help lists all eight.

10. Validate a File, or Write Its Schema

# Check an inventory or package definition against its schema; the kind is read from the document
cargoship validate ./cluster.yaml

# A config file declares no kind, so name the schema for it
cargoship validate --kind config ./cargoship-config.yaml

# Write the JSON Schema for one of cargoship's own file formats: inventory, package, or config
cargoship schema inventory -o ./inventory.schema.json

# Checksum a file, or one file inside an archive
cargoship dev sha256sum ./build/cargoship-distro-amd64.tar.zst

11. Record a Run for Audit

# Write a structured record of the run: what ran, against which package, against which fleet,
# and what changed. Written whether the run succeeds or fails, readable only by its owner.
cargoship apply ./build/cargoship-distro-amd64.tar.zst \
  --config ./cluster.yaml --confirm \
  --receipt-path /var/log/cargoship/receipts/apply-20260928-143000.json

# Strip everything that identifies the fleet, ready to attach to a bug report
cargoship dev redact-receipt ./receipt.json -o ./share.json

The receipt carries the invocation and the cargoship that ran it, the package’s digests and signature status, the cluster inventory, the phase-by-phase ledger with per-host change reasons and diffs, and any warnings the run raised under outcome.warnings – a successful run that left something on a host worth looking at says so there. redact-receipt renumbers the hosts host-01, host-02, drops the diff bodies – an engine configuration diff carries join tokens – and removes the cluster name, operator and command line, leaving what a maintainer triages from.

A fleet that keeps an audit trail sets the path once in the config file instead, under .distro.receipt_path, where apply, prepare, reset and engine-config-sync all pick it up:

distro:
  # {command} and {timestamp} expand per run, so each receipt lands in its own file
  receipt_path: /var/log/cargoship/receipts/{command}-{timestamp}.json

Those two placeholders are the only ones accepted; anything else is rejected before the run starts, rather than written out literally. --receipt-path overrides the configured value and takes the same placeholders.

12. Iterate on a Definition While Authoring It

Editing a distro.yaml normally costs a build and a separate install, and the artifact between them is most of the wait: a package is compressed on the way out of create and decompressed again on the way into apply, over bytes that never leave the machine. dev apply does both halves in one process and leaves the artifact out:

# build the definition and run the apply phases against it, with no package written
cargoship dev apply ./distro-defs --config ./cargoship-config.yaml --confirm

Everything after the build is the same code apply runs – values resolution, engine-configuration mapping and template rendering – so what reaches the hosts is what the built package would have put there. It takes the build-side flags that change what gets built, so a loop can still resolve content locally:

cargoship dev apply ./distro-defs --config ./cargoship-config.yaml \
  --content-store ./haul.tar.zst --confirm

The build still fetches what the definition declares, and still serves it from the shared cache when it is already there, so a second run after an edit usually reaches the network for nothing new. That cache is what Compile an Offline Package describes reclaiming with clean-cache.

This is for a definition under active edit, not for shipping. It writes no artifact to carry, keep, or sign, and it does not verify a signature – there is nothing to verify, because the package was built by the same process a moment earlier. A release still goes through create, sign and apply. See Authoring a Distro Package for the whole loop and what the build caches between runs.

13. Generate Definitions from a Template

A fleet’s package definitions usually differ in a handful of values – a version, an architecture, a CNI – and are otherwise the same file. dev render keeps them as one template plus a small values file per package, which is how cargoship’s own examples under example/ are generated:

# render a definition from a template and an input file
cargoship dev render --template ./distro.yaml.tmpl --values ./v1.36.4.yaml --out ./packages/v1.36.4

# render a definition and the values file beside it together, merging a common input first
cargoship dev render -t ./distro.yaml.tmpl -t ./values.yaml.tmpl \
  -f ./common.yaml -f ./v1.36.4.yaml -o ./packages/v1.36.4

Each --template is written to --out under its own name with .tmpl dropped, and every template renders against the same merged values, so a value that has to agree between a definition and the values beside it is written once. The template functions are the ones a package’s own values templates get – the sprig set, minus the functions that read host state – and a value path that resolves to nothing is an error rather than a placeholder in the output.

A rendered distro.yaml is checked against the package schema before anything is written, so a definition that renders but cannot be built is reported here rather than by create. cargoship create ./packages/v1.36.4 is the next step.

See Generating Definitions From a Template for the values-merge order, which template functions are available and which are deliberately not, and how to emit build-time {{ .Values.x }} expressions into the definition.

OpenTofu and Terraform

The same phases run from a declarative configuration through the OpenTofu provider, which lives in colonel-byte/terraform-provider-cargoship and consumes this repository as a library: cargoship_cluster converges a cluster – install, join and upgrade are one apply, because the engine version already on each host is what tells them apart – and cargoship_cluster_facts reads a fleet without changing it. It drives cargoship in process, so it still opens every SSH connection itself from the machine OpenTofu runs on.

It grew up here and moved out, so that it could be published under the name the provider registry requires; nothing in cargoship depends on it. See choice-tofu-provider-removal for what moved and what stayed.

Ansible Integration

colonel_byte.cargoship runs the workflows above as ordinary playbook tasks: cargoship_apply, cargoship_prepare, cargoship_reset, cargoship_kube_config, and cargoship_engine_config_sync, plus a cluster role that wraps them. Ansible supplies the inventory and runs one task for the whole fleet; cargoship still opens every SSH connection itself, from the management node the package was staged onto.

For driving zarf itself from a playbook, the colonel_byte.zarf collection lives in colonel-byte/ansible-collection-zarf. It grew up here and moved out; nothing in cargoship depends on it.

  • Running Cargoship as an Ansible Module - the modules, their parameters, check mode, and what changed means.
  • Generating an Inventory from Ansible - the group and host-variable translation, usable with or without the modules.
  • The Ansible Container Image - ghcr.io/colonel-byte/cargoship-ansible, which carries the binary and the collections together.

Configuration and Schemas

Cargoship relies on strongly-typed YAML definitions to govern its operations:

  • Cluster Inventories: Specify SSH configurations, credentials, host roles, profiles, and load-balancer addresses.
  • Distro Package Definitions: Map out the required binaries, OCI images, and layout settings.
  • Distro Runtime Configs: Configure the underlying distribution engine.

Inventories and package definitions are Kubernetes-style documents under cargoship’s own API group:

apiVersion: colonel-byte.dev/v1alpha1
kind: Cluster      # or Distro, for a package definition
metadata:
  name: fleet-cluster

The corresponding JSON schemas are automatically generated from Go structs into schema/, and cargoship schema writes any of them on demand. When authoring configurations in modern editors, refer to these schemas for real-time validation and autocompletion; cargoship validate checks a file against the right one without an editor.

An inventory authoring guide is available in Setting up an inventory, and the full set of guides – image tarballs, file and registry overrides, credential encryption, multi-architecture packages, firewalls – is under docs/guides/.

The zarf.dev group is deprecated

These documents used to declare apiVersion: zarf.dev/v1alpha1 with kind: ZarfCluster and kind: ZarfDistro. That group belongs to the upstream Zarf project, which defines its own kinds under it, so cargoship moved to a group it owns.

Both spellings are accepted, in any combination, and a document using the old one needs no change today:

OldNew
API groupzarf.dev/v1alpha1colonel-byte.dev/v1alpha1
Inventory kindZarfClusterCluster
Package kindZarfDistroDistro

Everything cargoship writes itself - cargoship inventory from-ansible, the Ansible collection, the OpenTofu provider, the generated example packages - now emits the new spelling. No removal date is set for the old one; when one is, it will be announced in a release before it lands.

Exit Codes

Cargoship is usually driven from a script on the management node, so a failure needs to say what kind of failure it was. Every command uses the same codes:

CodeMeaningWorth retrying?
0Success–
1A failure that is none of the below - a phase that ran and did not finish, an unrecognised commandNot on its own; read the error
2The invocation is wrong: an unknown flag, a bad flag value, the wrong number of argumentsNo - the command line needs fixing
3A file cargoship was pointed at is invalid: it fails its schema, or a config file has an undefined keyNo - the file needs fixing
4A host-changing command was run without --confirm. Nothing was touchedYes, with --confirm or --dry-run
5The fleet could not be reached or would not accept the credentials. No phase did any workYes - this is the one safe to retry unattended
130Interrupted with SIGINT, following the conventional 128 + signalYes

5 is the code worth branching on. It means cargoship stopped at the connection, so nothing on any host changed and a retry starts from the same state - unlike 1, which can mean a run stopped partway through and left a fleet mid-upgrade.

cargoship apply ./build/cargoship-distro-amd64.tar.zst --config ./cluster.yaml --confirm
case $? in
  0) ;;                                        # done
  5) echo "fleet unreachable, will retry" ;;   # safe to run again unattended
  4) echo "refusing to change hosts without --confirm" ;;
  *) echo "failed; read the receipt before retrying" ;;
esac

These numbers are a compatibility promise. A new classification gets a new code; an existing one is not repurposed.

Development and Build Workflows

Task automation is built using Mage, which drives builds, tests and code generation with the host Go toolchain.

Mage Automation

Mage handles tasks including local compilation, e2e test execution, schema updates, and documentation generation. Key generated files include:

  • build/cargoship_* (Release binaries)
  • docs/commands/* (Cobra command references)
  • docs/phases/* (Orchestration phase explanations)
  • docs/schema/* (Schema field reference, from the same struct reflection as schema/*.json)
  • docs/ansible/<collection>/module_*.md and docs/ansible/<collection>/role_*.md (Ansible collection reference)
  • docs/index.md and docs/security.md (this file and .github/SECURITY.md, with their links rewritten for the book)
  • docs/SUMMARY.md (mdBook layout manifest)
  • schema/*.json (YAML validations)

Continuous Integration (CI) and Releases

GitHub Actions workflows run lint checks, dependency validation, cross-compilation, and end-to-end tests for every pull request. Releases are managed through GoReleaser, automating build signing, verification, and asset publishing.
